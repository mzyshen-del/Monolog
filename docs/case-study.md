# Monolog 产品与交付案例

## 项目目标

Monolog 是一个面向访客的个人博客。访客需要在手机或电脑上阅读日记、留下留言；管理员需要登录后维护内容。我的交付目标是让这条流程在真实网址上可用，同时明确公开读取、管理员写入和访客留言各自的权限边界。本案例没有用户增长或商业收入指标，不能据此声称取得了相关成果。

## 我的职责与协作方式

我负责代码设计、关键方案选择、实现审查、测试结果审查和发布批准，并对交付结果负责。Codex 按这些设计与审查意见执行具体编码、测试和文档整理。以下决策描述的是我在项目中确定或审核采用的方案，不把具体编码工作写成我独立完成。

## 从需求到方案的关键决定

| 需要解决的问题 | 我确定或审核采用的方案 | 取舍 |
| --- | --- | --- |
| 访客能读内容，只有管理员能改日记 | 浏览器公开读取；管理员登录后用 Auth JWT 发起写入，由 Supabase RLS 判断权限 | 页面是否显示编辑入口不能代替服务端授权；过期令牌不能继续显示编辑能力。 |
| 访客可以留言，但网页不能持有数据库私钥 | 留言经过 Cloudflare Worker；Worker 验证 Turnstile、检查来源并限流，再用服务端密钥写入 | 增加了部署和运维环节，但避免把高权限密钥交给浏览器，也关闭了匿名直写入口。 |
| 网络故障时仍能尽量阅读内容 | 读取请求可在 Worker 和 Supabase 间切换，失败时显示本地缓存；写入失败不自动重发 | 阅读可以降级；留言与编辑不能因为重试而产生重复写入。 |
| 管理员忘记密码后能恢复管理能力 | 使用 Supabase 的邮件重置流程，在站内设置新密码 | 恢复令牌只用于设置新密码，不作为长期登录凭据保留在 URL 中。 |

这些决定分别落在 [前端请求与页面逻辑](../script.js)、[留言 Worker](../proxy-cloudflare-worker.js)、[数据库策略](../supabase-schema.sql) 和 [密码恢复流程](../reset-password.js) 中。静态页面无需构建步骤，部署于 Vercel；Worker 与 Supabase 承担服务端验证和数据存储。

## 交付与验证

项目已发布在 [Monolog 在线站点](https://mzyblog.vercel.app)。2026 年 10 月 19 日的线上验收记录包括：首页、日记和留言页可访问；公开读取正常；完成 Turnstile 后的测试留言写入成功；匿名直接写入留言表被拒绝；无效验证令牌和旧直写入口被 Worker 拒绝。项目负责人还在电脑和手机上验收了页面显示，并确认管理员登录、密码找回以及日记增删改可用。

[自动化测试](../tests/)覆盖读取故障切换、写入不重发、过期令牌、留言来源限制、限流、Turnstile 和密码恢复。测试使用模拟网络；它们验证关键分支，但不能代替持续的真实用户体验与线上监控。[部署步骤](../WORKER_DEPLOY_STEPS.md)记录了 Worker、密钥和数据库策略的切换顺序，便于复查交付过程。

## 已知边界与下一步

这是个人项目，当前仓库没有正式用户访谈、留存数据、商业收益或大规模流量验证的证据。因此我把成果表述为“完成可访问、可管理、具备基本保护的线上版本”，不把它包装成已验证的商业产品。若继续迭代，我会先确定目标用户与核心使用场景，再用真实使用反馈和稳定性数据决定功能优先级。
